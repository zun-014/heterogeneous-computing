### 问题

#### 异构计算是什么？

```
本质上是让 CPU、GPU、NPU 等不同资源按各自特性承担最合适的任务，并通过平台统一组织成可共享、可调度、可治理的算力体系。

对企业来说，真正重要的不是资源种类越多越好，而是能不能把这些资源组合成稳定可运营的生产能力。只有做到这一点，异构计算才不是概念，而是平台竞争力。
解决：
哪一部分给谁、什么时候开始、占多少资源、是否和别的任务并行、结果怎么同步回来，而且这样做到底有没有比单独执行更快。
```

#### 为什么需要边缘智能？

```
传统智能系统采用：将原始数据采集后上传云端，再进行AI分析，并返回结果。
这种方式依赖网络将大量原始数据上传到云端。对于工业监测、矿山安全、机器视觉等场景，一旦网络带宽不足、通信不稳定或云端响应较慢，就会直接影响实时性。

边缘智能则将计算能力部署到数据产生位置附近，使边缘设备能够直接完成数据预处理、目标检测、状态识别、时序预测、结果融合和异常判断等任务，从而使系统在不依赖持续云端连接的情况下仍具备一定的自主感知和决策能力。它的优势不仅是“降低一次模型推理的延迟”，更重要的是减少原始数据传输、缩短数据到决策的路径、提高现场响应能力，并将大量无价值数据在本地过滤，只把异常、特征或必要结果上传云端。因此，边缘智能实际上改变了整个智能系统的数据处理方式：云端更适合承担模型训练、全局分析、长期数据管理和策略更新，而边缘侧承担实时感知、快速推理和现场决策，两者形成云边协同。
```

#### 为什么仅仅依赖NPU还不够？

```
1.
NPU擅长卷积、矩阵运算、神经网络算子等。
但真实的边缘往往是（从数据采集-解码-标准化-推理-(前后)处理-判断-融合-上传...）
还有一大部分工作需要CPU完成。

所以：NPU=边缘智能系统的AI计算加速器

2.
多模型场景下NPU本身也会资源竞争
例如：模型ABc(行为、异常、人员检测)--->排队、核竞争、内存...
```

# 边缘异构推理论文总结

## 1. 性能评测与工作负载分析

**共同问题：不同任务适合哪种计算单元，性能瓶颈在哪里？**

| 论文                                        | 场景与方法                                                   | 自身特点                                                     |
| ------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| [1] Benchmarking Edge AI Platforms          | 在 Intel AIPC 上比较 CPU、GPU、NPU 的线性代数运算及 MobileNetV2、LSTM、TinyLlama 推理，分析规模、批量和访存特征对延迟、吞吐量的影响。 | 将基础算子与模型表现联系起来，为硬件选择提供依据；主要贡献是评测分析。 |
| [2] Neural Network Inference on Mobile SoCs | 在 Exynos 5422、Kirin 970 上评测 CNN 的性能与能效，利用 Roofline 模型分析计算、带宽瓶颈，并测试多计算单元协同处理图像流。 | 兼顾性能解释与协同执行，重点观察吞吐量和能效。               |

**合并理解：** 硬件优势取决于工作负载及软硬件配置，不能归纳为简单的固定的 CPU/GPU/NPU 排名。

[2] 还连接了“性能分析”与“异构协同”两个方向；其图像流并行不等同于单个算子内部切分。

## 2. 算子划分与 CPU–GPU 协同执行

**共同问题：如何让多个处理器共同加速一次模型推理，并避免协同开销抵消收益？**

| 论文                           | 核心方法                                                     | 对比与研究重点                                               |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| [3] CoDL                       | 采用适合各处理器的数据表示、混合维度划分及算子链，减少共享与转换开销；用感知非线性和并发影响的延迟预测器选择划分比例。 | 对比单 CPU、单 GPU 和已有协同方案；重点是算子内部的负载均衡与数据共享效率。 |
| [4] Partition-Aware Scheduling | 联合决定算子切分、设备分配和 DAG 执行顺序；采用分阶段搜索、关键性采样和延迟预测降低搜索开销。 | 对比仅调度、仅切分及离线联合优化；重点是协调算子内并行与算子间并行。 |

**合并理解：** 两篇都是算子切分与延迟预测，但 CoDL 更重视协同执行开销，[4] 更重视切分决策对整个计算图的影响。后者说明：**局部算子更快，不一定使全图更快**。其研究范围主要是固定形状的静态计算图。

## 3. 多模型并发、实时调度与资源分配

**共同问题：多个模型共享有限资源时，如何安排执行顺序、划分粒度和设备资源？**

| 论文                                | 场景与核心方法                                               | 主要区别                                                     |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| [5] GPU–CPU Collaborative Execution | 面向带截止期限的移动端 DNN 任务，将模型分为 GPU 前段与 CPU 后段，结合最早截止时间优先（EDF）和动态规划选择划分点。 | 重点降低截止期限违约率；属于模型层序列划分。                 |
| [6] ADMS                            | 面向移动端多 DNN，依据算子支持能力和调度粒度进行离线子图划分；结合负载、温度、频率以及截止期限、等待公平性动态调度。 | 重点是子图粒度与运行状态适应；                               |
| [7] MineInfer                       | 面向 RK3588 矿山边缘监测，将模型拆为可调度子图，联合搜索阶段、优先级和 NPU 核分配；用硬件实测评价随机搜索与遗传算法的候选方案。 | 重点是具体平台上的多模型调度参数优化；与串行、简单多线程及模块并发比较。 |

**合并理解：** 三篇均通过模型划分和资源调度改善多任务执行，但目标各有侧重：**[5] 按时完成，[6] 适应运行状态，[7] 搜索低延迟配置。** 子图划分是把多个算子组成可调度任务，与 [3][4] 将同一算子的计算量切给多个处理器不同。

## 4. 基于移动端CPU-NPU的深度学习模型部署与优化技术研究

《基于移动端CPU-NPU的深度学习模型部署与优化技术研究》，**模型划分不能只停留在“哪个算子放 CPU、哪个放 NPU”**。在 RK3588 上，作者先比较 ONNX Runtime（ORT）与 RKNN Runtime（RRT）在不同算子、不同数据规模下的性能差异，再通过数据传输时延预测指导模型分区，结合零拷贝、内存复用降低数据搬运与内存占用。

希望把 Transformer 中的大规模 MatMul 单独拆出来交给 NPU 时，RKNN-Toolkit 为适配 NPU 运算单元，可能自动把 MatMul 转换为：

```text
Transpose
    ↓
exMatMul
    ↓
Transpose
```

但大规模 Transpose 在 RKNPU 上并不一定高效，甚至可能被 RRT 回退到 CPU 后端执行。这样虽然 MatMul 本身在 NPU 上很快，前后额外产生的 Transpose 却可能把收益抵消。

**采用的办法**不是直接修改闭源 RRT，而是先修改 ONNX 计算图，在 MatMul 前后人为加入**互为逆变换的冗余 Transpose 组合**。这些组合在数学上等价于恒等变换，不改变模型输出；随后在 RKNN-Toolkit 转换和图优化过程中，与工具自动加入的 Transpose 形成可消除的冗余结构，从而尽量让最终 RKNN 子模型中只保留核心的 `exMatMul`。

```text
原始 MatMul
    ↓
直接转 RKNN
    ↓
Transpose → exMatMul → Transpose
    ↓
Transpose 可能成为瓶颈


改进：
ONNX 中人为加入互逆 Transpose
    ↓
RKNN-Toolkit 转换
    ↓
图优化消除冗余 Transpose
    ↓
尽量得到纯 exMatMul
```

**“决定某个算子放到 NPU”只是第一步，部署时还要考虑模型转换器、Runtime、数据布局、算子回退以及边界转换会不会改变原本的收益。**

另外：

```text
PC端
ONNX
 ↓
RKNN-Toolkit2
 ↓
.rknn
────────────────
RK3588端
.rknn
 ↓
RKNN Runtime（RRT）
 ↓
RKNPU Driver
 ↓
NPU
```

其中 RKNN-Toolkit2 主要承担模型转换、优化和性能评估；RRT（RKNN Runtime）负责加载 RKNN 模型、调用 NPU 驱动并实际执行推理。

## 5. Online Scheduling of CPU-NPU Co-inference for Edge AI Tasks

《Online Scheduling of CPU-NPU Co-inference for Edge AI Tasks》把问题进一步推进到**运行时在线决策**。场景是边缘设备持续处理实时视频流，每一帧都需要完整经过同一个 DNN：

```text
Frame t
  ↓
Layer1 → Layer2 → Layer3 → ... → LayerI
  ↓
该帧推理结果
```

但同一个网络层在不同帧上可以根据当时系统状态重新决定放在 CPU 还是 NPU。论文用 `x_i(t)` 表示处理第 `t` 帧时，第 `i` 层是否放到 NPU。

```text
Frame 1:
L1→CPU
L2→NPU
L3→NPU
L4→CPU

Frame 2:
L1→NPU
L2→NPU
L3→CPU
L4→CPU
```

原因是 CPU 执行时间并不是固定值，可能受到后台任务和共享资源竞争影响。论文因此把 CPU 层时延表示成随时间变化的 `C_i(t)`，同时考虑 NPU 时延、NPU 执行带来的精度损失，以及长期平均功耗约束。

两步：

1. **Lyapunov Optimization**：构造一个与长期功耗预算相关的虚拟队列 `Q(t)`，把原本需要考虑未来信息的长期优化问题，转换成每个时间槽都可以根据当前状态求解的在线问题。
2. **Greedy Knapsack**：对当前帧的所有 DNN Layer 计算“代价 / 性能收益”，排序并构造候选集合，再选择当前目标函数较优的一组 Layer 放到 NPU，其余 Layer 留在 CPU。

可以简单理解成：

```text
第 t 帧到达
   ↓
获得当前 CPU 时延状态 C_i(t)
读取功耗历史状态 Q(t)
   ↓
计算所有 Layer 的收益 / 代价
   ↓
排序
   ↓
贪心构造候选 CPU/NPU 映射
   ↓
选择当前帧较优方案
   ↓
执行
   ↓
更新 Q(t)
   ↓
第 t+1 帧重新决策
```

需要注意，论文中的贪心算法**不是按照 Layer1 → Layer2 → Layer3 的执行顺序逐层选择当前最优设备**，而是先对当前帧的全部 Layer 计算并排序，再近似求解一组 NPU-friendly Layer。它得到的是近似最优解，而不是严格全局最优。

这篇论文值得借鉴的地方是：它已经把 CPU/NPU 协同从“固定映射”推进到了**根据当前运行状态动态重映射**，而且优化目标不仅有时延，还同时考虑功耗与精度。

但也有明显值得继续分析的问题：

- 论文主要以 Layer 为调度粒度，没有显式建模频繁 CPU↔NPU 切换产生的 Tensor 传输、格式转换、同步和 Runtime 切换开销。
- 如果映射结果频繁出现 `CPU → NPU → CPU → NPU`，真实硬件上的边界代价可能抵消逐层调度收益。
- 每一帧重新计算所有层的收益、排序、候选集合，本身也会产生 Scheduler 计算开销。
- 论文主要使用 trace-driven simulation，真实 RK3588 Runtime 上的完整在线实现仍需要额外工程工作。

后期应注意：

```text
Layer-Level
    ↓
Operator Group
    ↓
Subgraph-Level

在不同粒度下综合比较：
计算收益
+ CPU/NPU传输
+ 同步
+ Runtime切换
+ Scheduler决策开销
```

这些论文总体属于 **边缘智能与移动计算中的异构神经网络推理系统优化**，主要研究如何高效执行已有模型。场景以端侧、移动 SoC 为主，[7] 进一步面向矿山安全监测。

- **性能理解：** 基准测试、工作负载特征分析、Roofline 建模与离线性能采样。
- **计算划分：** 模型分段、子图划分、算子内部切分及跨处理器协同。
- **执行优化：** 数据共享、同步与转换开销控制，DAG 调度、截止期限调度、状态感知调度和资源绑定。
- **决策求解：** 延迟预测、动态规划、启发式搜索，以及实测驱动的随机搜索和遗传算法。

可将它们的研究关系概括为：**理解硬件与任务特征 → 确定划分方式 → 协调执行与资源分配 → 改善延迟、吞吐量、能效或实时性。** 这是内容上的归纳，并非所有论文都覆盖完整链条。各文平台、负载和比较基线不同，不宜直接按加速倍数排名；也不能把仅在 CPU–GPU 上验证的方案视为已支持 NPU。

后续可扩展：

```text

→ 计算图与模型分区
→ 处理模型转换器 / Runtime 带来的额外问题
→ 建立跨设备 Cost Model
→ 运行时状态感知

→ 多目标动态调度

```

# 资源选择、任务划分与调度

## 1. CPU、GPU、NPU各擅长什么？

边缘设备的计算**资源有限**，而且不同处理器的能力与限制不同：

| 资源 | 典型优势                                         | 需要考虑的限制                           |
| ---- | ------------------------------------------------ | ---------------------------------------- |
| CPU  | 通用性强，适合控制逻辑、串行计算及灵活的任务处理 | 大规模密集并行计算通常不占优势           |
| GPU  | 适合并行度高的矩阵、卷积等计算                   | 小任务的启动、同步等开销可能抵消加速收益 |
| NPU  | 专门加速受支持的神经网络计算，通常具有较高能效   | 受算子支持、数据精度和工具链限制         |

**资源选择的依据是具体任务在具体设备上的表现。** 除了计算能力，还要看延迟、能耗、内存带宽、数据转换开销和算子兼容性，因此需要先进行性能测量。

## 2. 为什么不能全部交给一个处理器

- **全部交给一个处理器**：可能造成排队和瓶颈，而其他资源空闲，也可能把任务交给不擅长它的硬件。
- **所有任务同时运行**：可能争抢内存带宽、CPU线程或NPU核心，增加同步与数据交换开销；持续高负载还可能引发温升降频。

因此，**更多并行不一定带来更低延迟**。只有并行收益超过协同与竞争开销时，并行才值得采用。

## 3. “选谁执行、怎么划分”到“调度”

理解时可以先分清三个问题：

| 问题                                     | 对应概念                  |
| ---------------------------------------- | ------------------------- |
| 一个模型或算子要不要拆、拆成几块？       | 任务划分（Partitioning）  |
| 整个任务或各个分块交给哪个处理器？       | 资源选择与映射（Mapping） |
| 各部分何时执行、谁先谁后、哪些同时执行？ | 调度（Scheduling）        |

例如，把一个卷积算子拆成两块是**划分**，分别交给CPU和GPU是**映射**；安排两块何时启动、何时汇合，以及其他任务何时使用这些资源，就是**调度**。

这是一种理解顺序。实际优化中三者往往需要联合决定：某个算子同时占用CPU和GPU后，虽然自身更快，却可能让其他任务等待，使整体完成时间变长。

## 4. 调度

> **在依赖关系与资源约束下，决定谁先做、谁后做、在哪里做、哪些并行，以及分多少资源。**

- **依赖关系**：后续任务需要前序结果，输入未就绪时不能启动。
- **资源约束**：核心数量、内存与带宽有限，还可能受到功耗、温度和任务截止时间限制。
- **调度决策**：执行顺序、开始时机、处理器映射、并发组合，以及核心数量或工作量比例。

广义异构调度通常把资源分配和任务划分一起考虑。目标也随场景变化：降低延迟、提高吞吐量，或让更多任务按时完成。

异构协同调度通常分为三个层级：

```
任务级调度（Task-Level）                    
决定：哪个任务分配给哪个设备（CPU/GPU/NPU） 

算子级调度（Operator-Level）             
决定：模型里哪个算子放哪个单元             

线程级调度（Thread-Level）        
```

### 补充：调度器自身也存在成本

**调度决策本身也会存在成本**。如果每帧、每层都重新计算 CPU/NPU 收益并排序，虽然能提高适应动态负载的能力，但也会增加 Scheduler 计算开销；同时粒度越细，CPU/NPU 之间的数据传输、同步和 Runtime 切换越频繁。

因此后续不能只优化“某个算子执行多快”，而应把以下内容一起纳入 Cost Model：

```text
T_total
=
实际计算时间
+ CPU↔NPU Tensor传输
+ 数据布局 / 精度转换
+ 同步
+ Runtime切换
+ Scheduler决策开销
+ 排队等待
```

### 最佳粒度划分

与“最佳划分粒度”直接相关：

- 粒度过细：调度自由度高，但边界、传输、同步和调度成本增加。
- 粒度过粗：边界成本低，但可能失去异构资源组合带来的优化空间。

因此后续更合理的研究对象可能不是单个 Layer，而是根据实际任务形成 **Operator Group / Subgraph / Stage** 后再进行统一调度。

实际神经网络包含算子融合、分支、跳跃连接以及复杂的数据依赖关系，**并不是所有位置都适合划分**。最佳粒度也不是固定每几个算子组成一个子图，而是需要结合模型结构、硬件能力和 Runtime 限制，寻找合适的划分边界。所以最好需要进行:

| 分析阶段                  | 核心问题           | 主要考虑因素                                                 |
| ------------------------- | ------------------ | ------------------------------------------------------------ |
| 可行性分析（Feasibility） | 哪些位置能够切分？ | 计算图结构、数据依赖、算子支持、模型转换工具、ORT/RRT 能否独立执行对应子图 |
| 收益分析（Profitability） | 切分后是否值得？   | 子图计算时间、Tensor 交接、格式转换、同步、Runtime 开销及整体推理延迟 |

先通过可行性分析筛选出实际能够部署的候选划分，再通过 Profiling 和 Cost Model 比较不同方案的端到端收益。即使某个算子在 CPU 上单独执行更快，也不代表应该将其拆出；如果划分收益无法覆盖额外开销，保持连续子图甚至整个模型在 NPU 上执行可能更合适。

### 边界开销

边界开销一般有：数据搬运、格式转换、精度转换等等。主要产生在：CPU/NPU 之间的数据传输，还包括为使下一处理器正确使用上一子图结果而产生的一系列衔接成本。

开销也不是固定值。 它与切分位置、Tensor 数量和尺寸、数据精度、内存访问方式以及系统负载有关。即使跨设备切换次数相同，不同边界对应的实际开销也可能明显不同。

# 量化的核心特性及其在异构边缘计算中的必要性

## 1. 量化

量化是将神经网络的**权重和/或激活值用更低精度表示**，以减少存储、数据搬运和计算开销。例如，将 FP32 转换为 INT8。（以失去可接受的部分精度换取推理更快、体积更小、功耗更低、内存占用等）

它不是简单地把小数取整，而是通过缩放因子等建立映射：

e浮点值 ≈ scale × (整数值 − zero_point)` 

FP32 精度较高；FP16 是常见的低精度浮点格式；INT8 是常见的整数量化格式。严格来说，FP32 转 FP16 通常称为降低浮点精度，与 INT8 整数量化有所区别。

## 2. 主要收益与代价   

| 方面       | 核心特性                                                     |
| ---------- | ------------------------------------------------------------ |
| 存储与搬运 | FP32 → INT8 后，权重原始存储量约为原来的 1/4；若激活也量化，可进一步降低内存和带宽压力。 |
| 速度与能耗 | 在硬件和算子支持时，低精度计算可降低延迟与能耗；实际收益取决于实现，不能仅由位宽推算。 |
| 精度代价   | 舍入与截断会引入误差，可能降低模型准确率，需要校准与评估。   |
| 转换代价   | 量化、反量化及不同精度间转换会产生额外开销，可能抵消部分加速收益。 |

- **PTQ（训练后量化）**：对已训练模型进行量化，通常用少量代表性数据校准，成本较低。
- **QAT（量化感知训练）**：在训练或微调中模拟量化误差，帮助模型适应低精度，但训练成本更高。

## 3. 为什么要量化

CPU/GPU/NPU 的精度支持和执行效率不同：**CPU 灵活，GPU 常擅长并行浮点计算，NPU 通常对 INT8 等低精度计算更友好**，具体仍取决于芯片与软件栈。

量化的必要性主要来自三点：

1. **适配硬件能力**：让模型或算子使用目标设备支持且高效的数值格式，发挥 NPU 等加速器的优势。
2. **满足边缘资源约束**：减少内存占用、带宽需求和潜在能耗，为实时推理与多模型共存腾出资源。
3. **降低协同中的数据成本**：低精度数据可减少设备间传输量，但前提是接口支持；频繁反量化或格式转换可能削弱收益。

量化并非所有异构系统都必须采用，而是满足资源限制、发挥低精度硬件性能的重要手段。应结合准确率要求和端到端开销选择精度。

## 4. 与调度的关系

| 优化手段 | 关注的问题                                   | 主要作用                       |
| -------- | -------------------------------------------- | ------------------------------ |
| **量化** | 模型以什么精度表示和计算？                   | 优化单模型的计算与存储效率。   |
| **调度** | 哪个任务或算子由谁执行、何时执行、如何并行？ | 优化多任务与多硬件资源的协同。 |

二者相互影响：量化改变算子的执行时间、内存需求和可用硬件；调度应将这些变化，以及量化/反量化、数据搬运和资源竞争的开销一并纳入决策。

**理解顺序：选择合适精度 → 判断 CPU/GPU/NPU 的适用性 → 划分任务或算子 → 调度执行；实际优化时可迭代调整。**

# 需要保留的问题

通过最近两篇文献，进一步看到异构优化不仅是“划分与调度”，还涉及**怎样把划分真正落到模型图和运行时机制上**。第一篇通过修改 ONNX 计算图、构造可抵消的冗余 Transpose，使 RKNN-Toolkit 最终尽量保留纯 `exMatMul` 给 NPU，说明很多时候不是“决定某层放哪里”就结束了，还要考虑编译器 / Runtime 会不会额外插入算子、发生回退，甚至改变原本预期的收益。

第二篇则把问题推进到**在线动态调度**：每一帧到来后，根据当前 CPU 执行状态、长期功耗约束和各层的时延 / 精度代价，重新决定哪些层放 CPU、哪些放 NPU，并用 Lyapunov 优化结合贪心近似求解。

后续值得继续保留和分析的问题：

```
1. 模型转换器会不会改变划分结果？
   ONNX → RKNN 过程中是否会自动插入 Transpose、Reshape、量化转换或其他辅助算子，从而改变原本的 Cost Model？

2. 一次迁移是否真的值得？
   某个算子在另一个处理器上更快，并不意味着一定应该迁移；需要比较计算收益与 Tensor 传输、格式转换、同步及 Runtime 切换成本。

3. 最佳划分粒度是什么？ 
   Layer、Operator、Operator Group、Subgraph、Stage 不同粒度的自由度和边界成本不同，需要结合具体模型和数据规模分析。

4. 运行时状态怎样进入决策？
   A55/A76 利用率、NPU Core0~2 占用、队列长度、频率、温度、内存和带宽压力、Deadline 等都可能改变原本离线 Profiling 得到的最优方案。

5. Scheduler 自身是否值得？
   如果每一帧都要重新计算收益、排序和搜索映射，调度器自身的 CPU 占用和决策时间是否会抵消动态调度收益？

6. 逐层调度是否过细？
   理论上的 Layer-Level 动态映射在真实 RK3588 上可能造成频繁 CPU↔NPU 切换，实际更值得研究的是连续子图或阶段级调度。

7. 优化指标应该如何组合？
   延迟仍然重要，但实际边缘网关还可能需要同时分析吞吐、能耗、资源利用率、Deadline Miss Rate、传输代价、热稳定性及多任务公平性。
```
